# Plugin Board Previews — Design

**Date:** 2026-08-05
**Status:** Approved
**Closes:** [#1436 — \[Docs\] add Note previews](https://github.com/Fiestaboard/FiestaBoard/issues/1436)
**Scope:** Four repos — `Fiestaboard/FiestaBoard` (manifest contract, validation, bundled plugins, seed + sync), `Fiestaboard/FiestaUI` (`BoardTeaser`), the docs site (`docs-site/`), and eventually the 50 `fiestaboard-plugin--*` repos (backfill, not this project)

## Goal

Replace hand-maintained plugin screenshots with rendered board previews driven by manifest metadata. Plugin authors describe what their board looks like as *data*; the docs site renders it live, at any board shape, in any theme, without images and without animation.

## Current state (measured 2026-08-05)

- **Screenshots are a maintainer tax, not a contributor artifact.** 49 of 50 registry plugins carry all three PNGs (`docs/board-display.png`, `docs/white/`, `docs/black/`). They are clean renders of the board component, script-generated by the maintainer (`scripts/fix_plugin_screenshot_names.py`, `scripts/seed_screenshot_data.py`) — not authored by plugin developers. ~7 MB of binaries across 50 repos.
- **Nothing in the app consumes them.** `screenshots` appears only in `src/plugins/manifest.py`; the Integrations page never renders it. Those 7 MB exist solely to feed docs-site.
- **They have already drifted.** `muni`'s PNG shows a 5-row arrivals list; its `demo.flagship.template` is `Muni Arrivals` / stop name / formatted / blank / blank / `Stops 2`. Same for `stocks`.
- **All 50 are flagship 22×6.** Nothing for Note or Note Array owners.
- **The metadata groundwork already exists.** All 50 registry manifests ship `demo.flagship` *and* `demo.note` templates with `line_metadata`; every simple variable has an `example`. Gaps: array variables have no example rows, and art variables carry placeholders (`sun_art.example == "(art pattern)"`), so the demo blocks are not directly renderable.
- **The renderer already exists.** FiestaUI exports `StaticBoardDisplay` — *"Zero-overhead static board display for previews. No useState, useEffect, useRef, or animation logic."* It is present in the vendored tarball docs-site already installs, and `HeroBoard` proves live multi-shape rendering works on the site today.
- **Bundled plugins still use the legacy flat `demo` shape** (`{name, device_type, template, line_metadata}`), while all 50 external plugins use the per-device keyed shape. `plugins/_template/manifest.json` teaches the legacy shape.

### Why #1436 has been hard to close

Plugin board content currently lives in **four** disconnected places:

1. `PLUGIN_DISPLAYS` in `web/tests/generate-screenshots.spec.ts` — 33 entries of hand-authored literal rows, with `device_type: "flagship"` hard-coded at line 68. **This is what actually generates the PNGs.**
2. `demo.flagship` / `demo.note` templates in each plugin's `manifest.json` — 50 plugins, both devices, with `{{variable}}` placeholders.
3. The committed PNGs in each plugin repo (`docs/`, `docs/white/`, `docs/black/`).
4. Mirrored copies in `docs-site/static/img/<plugin>-display.png`.

They disagree, and #1436's existing analysis was scoped against source 1 while the design intent lives in source 2. That is precisely why `muni`'s PNG matches the Playwright spec but not its own manifest.

This design collapses all four into one source of truth. Two facts make it far cheaper than the issue's prior estimate:

- **`PLUGIN_DISPLAYS` is already in the exact literal-rows format `previews[]` uses**, so 33 flagship previews port across mechanically.
- **All 50 plugins already have a `demo.note` layout authored.** The issue's blocker #1 ("each plugin needs a hand-authored 15×3 template — content/design work, not a mechanical re-render") is mostly already done; what remains is substituting example values into an existing 15×3 layout, not designing one.

Blocker #3 ("binary assets must be regenerated from the running dev container via Playwright and committed") disappears entirely — there are no binaries.

## Decisions (with rationale)

1. **Two-tier model.** Store cards get a one-line *teaser*; detail pages get full *previews* in any shape the author declares. Rejected: full boards on cards (~7,000 DOM nodes for 50 flagship boards; Lighthouse fails past 3,000).
2. **Previews are literal board rows,** not templates the site resolves. Authors write what the board looks like. Rejected: template + `sample_data` resolved through the engine — truthful to the template, but costs a generation step, a CI staleness gate, and hand-written nested array fixtures. Literal rows can drift from the real template; the mitigation is that fixing one is a text edit in a reviewable diff, not a regenerated PNG.
3. **Teaser is explicit and required, with no runtime fallback.** Auto-slicing the first 15 tiles of a flagship layout yields fragments like `     STOCK PRIC`. A missing teaser is a validation error, not a silent degrade.
4. **Purely additive.** `screenshots` stays valid, READMEs keep their images, existing PNGs stop being *consumed* rather than being deleted. No plugin author receives a "remove your image" PR.
5. **Central seed now, backfill later.** A generated `plugin-previews.json` in this repo covers all 50 plugins; manifest values override it as authors adopt. The site is complete on day one with zero cross-repo coordination.
6. **Transition plugins are exempt.** `plugin_type: "transition"` plugins (`typewriter`, `slot_machine`, `simple_dissolve`, `quiet_library`) have no data to display, and their entire purpose is animation — which this design deliberately does not render.

## The contract

Two additive manifest fields:

```json
"teaser": "{66}AAPL +1.88%",
"previews": [
  { "label": "Flagship", "device_type": "flagship", "rows": [ "… 6 rows …" ] },
  { "label": "Note",     "device_type": "note",     "rows": [ "… 3 rows …" ] },
  { "label": "Wide",     "device_type": "note_array",
    "notes_wide": 2, "notes_tall": 1, "rows": [ "… 3 rows × 30 cols …" ] }
]
```

`previews[0]` is the detail-page hero. `label` is optional and defaults from the resolved shape.

## Validation rules

Implemented in a new `src/plugins/previews.py` (keeping `manifest.py`, already ~780 lines, from growing), surfaced through `validate_manifest()` and `scripts/validate_plugins.py`.

- **Teasers are measured in tiles, not characters.** `{66}` occupies one flap, not four characters. The rule is 1–15 tiles, mirroring `TemplateEngine._count_tiles()`. 15 is the Note width — the narrowest board FiestaBoard supports, so a teaser fits every device.
- **Teasers are literal.** A `{{variable}}` reference is an error; there is no data to resolve against at render time.
- **Preview rows are checked against resolved device geometry** via `resolve_dimensions()` from `src/devices.py`. Rows may be *fewer* than the device's row count (padded with blanks), never more. Each row must fit within the column count, counted in tiles.
- **Overflow and unmappable characters are errors, not silent corrections.** `text_to_board_array()` truncates at `col_idx < cols` and maps unknown characters to `SPACE`; validation reuses its `COLOR_MARKER_PATTERN` and `BoardChars.get_char_code()` but *reports* what that function would have silently swallowed.
- **`note_array` previews are capped at 4×4** (60×12 = 720 tiles). Hardware allows 8×8 (`MAX_NOTES_PER_AXIS`), but 2,880 tiles on a documentation page is not a preview. Judgment call, cheap to revisit.
- **Maximum 6 preview entries per plugin.**
- **Data plugins require both fields; transition plugins must not declare them.**

## Store page

Card becomes name, category badge, description, author, and a 15-tile split-flap strip. No board image, no full board.

- ~18 DOM nodes per card → **≈900 nodes for all 50**, versus ~7,000 with flagship boards. No virtualization required.
- Page weight drops from ~2.4 MB of PNGs to effectively nothing (~40 KB of JSON for every plugin and device, ~10 KB gzipped).
- The strip follows site theme (dark → black board, light → white), reusing the `useColorMode` pattern already in `BoardScreenshot`.
- The directory's black/white toggle is **removed** — it existed only to choose between two PNGs.
- `role="img"` with the plain-text teaser as `aria-label`, so assistive tech announces `AAPL +1.88%` rather than fifteen `div`s.

## Detail page

- Device tabs across `previews[]`, one board mounted at a time, so DOM stays flat regardless of how many shapes an author declares.
- Board color toggle stays here — now a render prop rather than an image swap.
- README fetch unchanged; the PNG hero is dropped.

## Data flow

`plugin-previews.json` at the repo root, committed, imported at build time exactly as `plugin-registry.json` is today. No runtime image fetches — this also removes the current per-card `raw.githubusercontent` requests.

`scripts/sync_plugin_previews.py` runs inside the existing `scheduled-maintenance.yml`: for each registry entry, read the plugin's `manifest.json`; if it declares `teaser`/`previews`, those win; otherwise **preserve the existing hand-authored entry**. Entries are removed only when a plugin leaves the registry. That preservation rule is what makes "seed now, backfill later" safe — adopting the fields silently upgrades an entry, and doing nothing never regresses one.

## New component

`BoardTeaser` in FiestaUI — one row of N tiles built on the exported `parseLine()`, sharing `StaticBoardDisplay`'s tile styling. Ships with a story and an a11y test per the FiestaUI contract. Everything else renders through `StaticBoardDisplay`, which already handles every shape via `deviceType` + `notesWide`/`notesTall`.

## Phasing

| PR | Repo | Contents |
|---|---|---|
| 1 | FiestaBoard | Contract, `src/plugins/previews.py`, validation, tests, bundled plugins (`countdown`, `date_time`, `random`), `_template`, docs |
| 2 | FiestaUI | `BoardTeaser` + story + a11y test, released as a minor |
| 3 | FiestaBoard | `plugin-previews.json` seed (50 plugins), `sync_plugin_previews.py`, workflow wiring |
| 4 | FiestaBoard | docs-site store page + detail page rewrite |
| 5 | plugin repos | Backfill `teaser`/`previews` into manifests — not part of this project |

PR 3 ports `PLUGIN_DISPLAYS` (33 flagship entries) out of `web/tests/generate-screenshots.spec.ts` into the seed. Once PR 4 lands, that spec's plugin-display pass is dead code and its `PLUGIN_DISPLAYS` array should be deleted; the spec's *app UI* screenshot passes stay, since those photograph the product and cannot be replaced by a board renderer.

## Out of scope (deliberately)

- The 25 `docs/plugins/*.md` pages. They are stale (`"26 built-in plugins"` against 50 in the registry) and duplicated into 75 `versioned_docs` snapshots (31 MB), and `/plugins/detail?id=` is a client-side query route that is close to invisible to search engines. Worth a separate project; keeping this one additive.
- The homepage. `HomepageFeatures` uses six PNG illustrations (268 KB) that `lucide-react` could replace, and `static/img/guides` is 7.5 MB — but those are genuine product screenshots a board renderer cannot replace.
- Bundled plugins (`countdown`, `date_time`, `random`) do not appear in the store directory at all today, since it is driven purely by `plugin-registry.json`. Noted for a later round.

## Risks

- **Literal previews drift from real plugin output.** Accepted per decision 2. Mitigated by review cost being a text diff, and by previews sitting next to the `demo` templates they illustrate.
- **50 teasers are 50 small judgment calls.** Mitigated by landing in one file in one PR rather than 50 repos.
- **Seed and manifest can disagree** once authors adopt. Resolution order is fixed and documented: manifest wins, seed is the fallback, entries are never silently emptied.
