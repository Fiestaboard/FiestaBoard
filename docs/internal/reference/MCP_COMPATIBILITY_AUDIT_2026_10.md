# MCP display and canvas compatibility audit

Audited revision: `f84b1d3d3`, October 18, 2026. The table records the original findings and source locations. Implementation is in progress on `fix/mcp-display-plugin-compatibility`, based on `next` at `643fa8b2c`. Candidate fixes and executable regressions are present; integrated verification is pending. Findings 12, 20, 22 and 23 already have upstream changes on this newer base and retain regression coverage here.

The reported 12×29 detection error is reproducible. The MCP tool reaches a legacy route that always selects the Vestaboard output action, even for a valid FiestaPanel. That action rejects a layout which the panel itself supports. Separately, the information external clients receive does not reliably identify pixel capabilities or teach canvas authoring. Fixing detection alone will not fix the art workflow.

There are **39 actionable findings: 37 reproduced behavior, discovery, or conformance defects, plus two source-confirmed frontend context gaps**. The plugin-display expansion adds 16 findings and extends discovery finding 02 upstream. Fifty-one regression cases capture the reproduced defects. Several cases exercise different consequences of the same finding; they are not counted as separate bugs.

An LED-styled FiestaPanel currently still consumes a character grid. It is different from a pixel-capable output such as a Pixoo. The server should expose that distinction and choose a supported authoring path. The supplied error does not establish which kind of matrix the user's installation has, so the audit covers both without claiming to have inspected that installation.

The output-management tool surface also lacks equivalents for listing output models/actions, creating output-plugin boards, and editing their font/tile layout/configuration. These are capability gaps to address with the discovery redesign, rather than additional counted runtime bugs. Existing `add_board` remains Vestaboard-oriented; `create_panel` covers virtual panels.

The fix needs a shared, versioned display description rather than additional built-in display branches. A client should be able to ask about any connected board and receive:

| Information | Required distinction |
| --- | --- |
| Identity and provenance | Board ID, output/plugin ID and version, output API version, selected model, and declaration revision. |
| Geometry | Character grid versus physical pixel dimensions, effective font/tile/layout settings, and whether geometry is configured, declared, or observed. |
| Authoring capabilities | Full supported character/markup document, palette/color model, fonts/icons, text/cell/pixel/canvas support, constraints, and explicit fallback behavior. A matrix appearance alone does not establish pixel-canvas support. |
| Delivery capabilities | Effective per-board animation/sequence/native-transition support, limits, send floor, timeout, and readback support/cost. Separate plugin-wide declarations from resolved device behavior. |
| Configuration and actions | Configuration schema and masked values/status; discoverable action IDs, input schemas, descriptions and effects. Invoke actions through the existing generic output mechanism using the selected board context. |
| Observations | Connection/error state, last send outcome, and readback with timestamps/source. Distinguish cached intended content from device-confirmed content and report unavailable observations explicitly. |

Large model, charset, or action catalogs can be referenced as versioned resources with bounded listings; the board summary should carry enough resolved information to choose the correct authoring path. Preserve plugin-defined extensions in a namespaced form, with unknown features explicitly unsupported until a consumer understands them. Do not infer missing capabilities from the plugin name. The same resolved profile must drive prompts, validation, preview, delivery, readback, and cache identity.

Current API1 has documented closed technology/font/icon vocabularies and minimum geometry constraints. It cannot promise literally every future display technology without evolving that contract. Also, base-class capabilities deliberately default to the first model: a multi-model plugin must override them today. A passing characterization test records that limitation; it is **not counted as another bug**. The redesign should make selected-model capability resolution explicit so authors do not accidentally advertise another model's limits.

Fix order should follow these dependencies:

1. Close output-secret masking gaps (32, 38), then repair shared configuration/action validation and construction cleanup (33–37).
2. Establish complete declarations and effective per-board profiles, truthful lifecycle results, and correct cache identity (01–05, 24–25, 29, 39). Expose generic output discovery/configuration/actions through MCP.
3. Make authoring guidance capability-aware and preserve complete drafts (15–19, 26–27).
4. Align validation, previews, activation, copying, readback, and rich delivery across text/canvas/animation paths (06–14, 28, 30). Preserve errors and resize warnings (04, 20).
5. Repair quiet-hours persistence and cross-surface queue behavior (21–23).
6. Extend SDK conformance (31) and end-to-end tests using independent valid plugins: custom charsets, multiple models, monochrome/RGB pixels, conditional settings, failed opens, and different animation/readback modes.

The audit uses isolated Docker runs with networking disabled and temporary storage. The image's output seed matches the repository's `outputs.lock.json`. No existing running installation or real display was modified. An HTTP JSON-RPC test exercises initialize, tool discovery, page creation/readback, resource discovery/readback, and a domain error through the production MCP app builder.
