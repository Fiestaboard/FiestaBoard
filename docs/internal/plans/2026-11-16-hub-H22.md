# H22 expired override ownership implementation plan

> **For agentic workers:** Use superpowers:executing-plans, with an independent Astra review at the committed head.

**Goal:** Status polling must not steal a pending expiry revert from the display engine.

**Architecture:** Active reads filter expired overrides without deleting them. The existing locked consume path removes each expired record once. Store and engine classify the returned record at one captured UTC instant, preventing a second revert when expiry passes between their checks.

**Tech stack:** Python, FastAPI, pytest, threading events, existing JsonStore RLock.

**Spec:** Program `status/hub-H22.md`, MASTER-PLAN H22, original PR #2481 review section 1.5.

## Constraints and scope

- Work only in `fb-wt/cx-hubH22`; base and PR target `v11`.
- Preserve per-board isolation, explicit cancellation and legacy boot migration.
- No sleeps in new concurrency tests; use bounded event waits only as deadlock guards.
- No UI changes or new storage schema. No crash-safe exactly-once delivery promise.
- Existing consume/set lock protects replacement from stale deletion; do not extend settings locks across device I/O.
- No merge, publication, comments or VRT approvals. Respect the shared Docker limit and `WRAPUP`.

## Review focus

- Read at exact expiry: inactive response, no write, pending page/blank revert retained.
- Clock crosses expiry during a consume: defer until the next pass, then apply once.
- Two consumers or a concurrent replacement: one expired claim, replacement retained.
- Multiple boards: consuming one leaves the other's pending state untouched.
- Cancellation and legacy loading: existing explicit-clear and restart semantics retained.
