# Production accessibility audit

## Problem and scope

The existing route accessibility helper disables contrast and filters out
moderate/minor findings. Its default desktop project and selected states do not
establish WCAG 2.2 AA accessibility of the published v11 application.

Add an explicitly invoked production audit runner with a separate configuration.
The first step surveys settled routes at 1280, 900 and 390 CSS pixels in both
themes. It retains full-document axe results, including all violation impacts and
incomplete checks, enables contrast and target-size checks, and records exact
campaign identity. This bounded survey does not cover all flow states or replace
keyboard, assistive-technology, contrast, motion, target-size or reflow evaluation.

## Isolation and provenance

- Run only against the single authorized shared hub with isolated synthetic data.
  Verify exclusive PROD access and the total container cap before Docker use.
- Require an explicit target origin, synthetic-data acknowledgement, immutable
  image digest, source revision, authentication mode and campaign label.
- Keep published alpha.3 findings separate from each unmerged candidate. A newer
  test-harness revision does not change the application revision being audited.
- Do not import the normal global setup or helpers: they delete persisted data
  and can invoke Docker/auth setup. Block unexpected mutating requests.
- Use a dedicated audit filename/configuration so normal regression discovery
  does not silently run against an unqualified target or report missing fixtures
  as accessibility passes.

## Execution and evidence

1. Prepare the dedicated runner and review its isolation and state assertions.
2. Pin the actual booted published image, verify health and synthetic seed, then
   run one audit file with one Playwright worker. Retain screenshots, full axe
   JSON, precondition failures and browser/axe versions.
3. Expand from the initial route survey to the route/state inventory in the
   program's `reviews/PROD-prodA11y.md`. Require the intended settled state before
   scanning; redirects, loaders and absent fixtures cannot become passes.
4. Perform natural keyboard walks and record focus, dialog containment/return,
   error associations, names, contrast, zoom/reflow, text spacing, pointer targets
   and motion. Record actual screen-reader observations where supported, and
   mark unsupported or unrun checks explicitly.
5. Reproduce defects with meaningful regression failures before source fixes.
   Coordinate existing Home/editor ownership; the Panel fullscreen action is a
   source-supported keyboard concern requiring runtime reproduction. Use or
   extend FiestaUI for presentation primitives.
6. Validate candidate fixes separately with relevant regression/coverage, axe,
   typecheck, lint, formatting and build checks. Preserve baseline failures.
   Require independent exact-head review and observed CI results for a fix PR.

## Readiness limits

This plan and the runner are not accessibility certification. An axe-clean page
does not prove WCAG conformance, and a blocked test is not a pass. The production
gate remains open until the full criterion/state evidence has been assessed.

Local Docker execution is currently deferred by concurrent PROD jobs. The
dispatcher inventory is the explicitly authorized process-inspection substitute
in the program bus; stale inventory never proves exclusion. Do not create a
second local or hosted hub to bypass the serialization rule.
